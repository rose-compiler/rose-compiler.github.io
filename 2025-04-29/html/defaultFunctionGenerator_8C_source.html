337  * 1. Need to introduce destructor calls where they would be
338  * called implicitly. Currently, we only introduce destructor
339  * calls, i.e., this->~Foo(), within a destructor Bar, where
340  * Foo is a base class of Bar.
341  *
342  * 2. Need to fix constructor calls in which the constructor
343  * may be inferred, but is not directly specified. In cases
344  * in which the constructor had not been defined (prior to
345  * running this traversal) but was invoked, SAGE might not
346  * have a method declaration to use at the call site. In such
347  * cases, the method dangling from a SgConstructorInitializer
348  * might be NULL (e.g., if it represents a call to a default
349  * constructor) or where we would expect a SgConstructorInitializer
350  * we instead see a SgAssignInitializer (e.g., if it represents
351  * a call to the copy constructor). Please see the above
352  * note on 'inferring which constructor is invoked' above.
353  *
354  * NB: We have introduced calls to all special methods
355  * where they were implicit (except for destructor calls
356  * as noted in (1) ). These calls are different:
357  * there _are_ explicit calls, but they do not directly
358  * name the invoked special method.
359  *
360  * 3. Where invocations of special methods are introduced, they
361  * are not necessarily introduced in the proper order.
362  * The procedure for introducing implicit methods is as follows
363  * (please see generateImplicitInvocations). For a given
364  * special method C::m, we determine all superclasses C' of C.
365  * We then determine all base classes C'' invoked within C::m.
366  * Roughly, this means any method C''::m invoked from C::m.
367  * Note however that if m were a copy constructor, then we would
368  * also collect any class C'' whose _default_ constructor was
369  * invoked. Now, for all superclasses C' of C (visited in
370  * order as returned from get_inheritances()), if C' is not in
371  * C'', we generate a method call. Presumably, methods are
372  * supposed to be called according to some special order,
373  * e.g., the order in which their base classes are listed in
374  * the inheriting class' definition.
375  *

377  * Should there be? I think so. For example,
378  *

384  *

386  *
387  * The invocation of C's default constructor should only invoke
388  * A's default constructor once. Currently, we will make the

615 // Describe how new nodes should be added to the AST.
616 // Debugging purposes: mark nodes as transformation nodes
617 // (i.e., generateCompilerGeneratedNodes = false)
618 // In this case they will be emitted by the unparser
619 // and passed to the backend compiler.
620 // "Real" runs: mark nodes as compiler generated
621 // (i.e., generateCompilerGeneratedNodes = true)
622 // In this case they will _not_ be emitted by the unparser
623 // and will _not_ be passed to the backend compiler.
624 // Thus they only exist in the AST for analysis purposes,
625 // which is our intent. There are a few reasons for doing this:
626 // 1. We don't want to confuse the user by introducing
627 // code which isn't in the original program.
628 // 2. We introduce definitions a bit liberally. e.g.,
629 // we always provide a default constructor if one does
630 // not exist. This is not consistent with the C++
631 // language definition, which states that a compiler
632 // should only introduce a definition "if needed"
633 // (i.e., invoked).
634 // 3. (and most importantly) Some of the source code
635 // we introduce will not compile. In particular,
636 // in the face of multiple inheritance of the same
637 // base class, we may introduce ambiguous constructor
638 // calls. These should not confuse analysis, but may
639 // upset the backend compiler. Please seee the
640 // comment above regarding "multiple inheritance"
641 // under "known issues".
642

644 // rather than compiler-generated nodes. The former will be unparsed,
